# Scout map: CEM route planner + closed-loop evaluation harness (both worlds)

Read-only scout, 2026-09-21. Claims were checked in code or data; plan gaps are stated explicitly.

## 1. End-to-end recipe to evaluate a NEW risk checkpoint closed loop

One script builds pools, runs CEM and locks picks for both worlds: `scripts/planner_arms.py`.

- Inputs: `--cases <dir with <g>.json + routes/<g>/route_00.json>`, `--world crm --map-root artifacts/traverse/crm_f104_v1/map_root` (OptiX static depth map via `f104_n2_dataset.init_map`, `planner_arms.py:82-85`) or `--world rigid --rigid-arena assets/traverse/arena_f104_50h_v1` (heightmap via `gen_planner.set_map`, `gen_planner.py:35-42`), `--models '<glob of N2-format .pt>'`, `--arms A,B,C,D,E,F`, `--fixed2` for the 2 m/s geometry-only family (`planner_arms.py:60-80`). Exact invocations used: `artifacts/traverse/crm_night2_v1/planner/run_planner_arms.sh:8-11`.
- Base route = `route_00.json` of the case (`planner_arms.py:41-48`); pose = `layout.start_xy/start_yaw`, NOT the settled pose.
- Arm A = deployed one-shot 256 (`f104_n2_iter.oneshot`, `:327-333`; rng tag `crm_proposal`/`gen_night2`, fixed-2 tags `crm_fixed2`/`gen_fixed2`, `planner_arms.py:85,92`), checked route-by-route against `gen_planner.proposal_pool/fixed2_pool` (`selftest`, `f104_n2_iter.py:343-359`). Arm B = CEM 4x64 (`plan_iter(rounds=4, n=64, elite_frac=0.15, sd_floor=0.15, weighting='cem')`, `f104_n2_iter.py:227-324`): round 0 = 9 anchors + prior draws to 64 valid; later rounds refit mean first; every round is one batched corridor build + one ensemble score; pick = argmin objective over everything evaluated (`:312-315`). Seeds `md5(group+tag)` (`:25-26`). Validator: `GP.safe_validate` with `MPPIConfig(max_speed 6, curvature 0.125, half-extent 40)` (`gen_planner.py:30,94-99`).
- Outputs (`planner_arms.py:142-194`): `<out>/picks/<g>.json` (per arm: route_id, index, kind, round, theta, z_mean, z_pess, P, T, J, log), `<out>/routes/<g>__<first arm>.json` (collector route format, deduped by sha256 of content), `tasks.json` rows `{id, group, case, route, run, tier=group index, episode_seed, arms, sha256[, ref_id][, arena, shard]}`, `tasks_new_only.json` (A rows equal to the reference pick get `run=false`), `summary.json`, `PICKS_LOCKED.sha256`. Observed: CRM 200 groups -> 1,137 distinct routes, 937 new drives, A == locked eval_v1 picks 200/200; rigid fixed-2 -> 1,000 routes, A == gen_v1 `n2_fixed2` 200/200 (`planner/iter_crm/summary.json`, `iter_rigid_f104_fixed2/summary.json`).
- Ship + drive, CRM: rewrite `route` to `night2/<name>/routes/<id>.json` relative to `CRM_ROOT=/work1/dannegrut/harry/experiments/crm_f104_20260916` (observed `iter_crm/tasks_cluster.json`; the rewrite for CEM arms was an unsaved one-liner, `scripts/n2_grad_ship.py:253-258` does it for gradient arms with `--cluster-prefix`), rsync routes + tasks, then `scripts/crm_launch.sh <tasks> <out> configs/crm_main.json [hours]` (one sbatch per GPU partition, `crm_launch.sh:9-21`) -> `scripts/crm_collect.sbatch` -> `scripts/crm_worker.py` (mkdir claims, retries, `crm_collect.py --case --route --out --chrono-data --horizon-s 120 --episode-seed --crm-config`, `crm_worker.py:91-99`; rows ordered by `tier`, `:77-79`). CRM is bit-identical across GPU types (`crm_f104_v1/REPORT.md:48-49`), so no per-node grouping is needed. `--episode-seed` is provenance only (`crm_collect.py:393`).
- Ship + drive, rigid: `scripts/n2_rigid_eval_tasks.py --picks-dir <out> --case-prefix cases_test_f104/cases --route-prefix night2_iter_f104_fixed2/routes --shards 24 --out tasks_gen.json` (shard = md5(group) % 24 so all arms of a group run on one node, `n2_rigid_eval_tasks.py:8-10`); `scripts/gen_array.sbatch` (`GEN_ROOT=$campaign/gen_v1` hardcoded, `:54`) -> `scripts/gen_runner.py` (`gen_collect.py` per row, thread pool, `:21-34`); submit `GEN_TASKS=... GEN_OUT=... sbatch -p mi2101x -c 16 --array=0-23 --export=ALL gen_array.sbatch` (`crm_f104_v1/scout/planner_eval.md:132-137`).
- Analysis: sync `runs/<route_id>/` back, then `scripts/n2_planner_analyze.py --picks <out>/picks --runs <runs> --arms A,B,... --primary B:A --contrasts ... --label fail|unsafe [--ref-runs --ref-arm] --out results.json`. `goal_reached` = `outcome.status == 'goal_reached'` via `f104_n2_analyze.labels` (`f104_n2_analyze.py:16-24`, first 20 frames skipped; `unsafe` adds backward-motion tests); needs only `trajectory.npz` + `outcome.json`. Paired stats: exact two-sided McNemar on discordant groups + 4,000-resample group bootstrap of the rate difference (`n2_planner_analyze.py:261-263, 298-304`), groups with ALL arms present (`:293`). Per-arm rates incl. median time/work/mean predicted P (`:311-316`). Terrain-feature-clustered CI + sign test: `scripts/n2_cluster_ci.py` (9 clusters). `results.json` = `{summary:{PRIMARY_B:A{n, rate_a, rate_b, diff, ci95, a_worse, b_worse, p, identical_picks}, contrasts, rates, AA_reproduction}, per_group:{g:{arm:{fail, unsafe, status, elapsed, max_tilt, tilt30, work_kj, route_id, P, z, T_cmd}}}}` (verified on `eval_iter_crm/results.json`, `eval_rigid_f104_fixed2/results.json`).

## 2. What the planner needs from the model at inference

- Loader: `gen_planner.RiskModel(pattern)` (`gen_planner.py:154-168`) builds `gen_riskmodel.Net(ck['cin'], ck['nctx'], arch=ck['arch'], layers=...)` per sorted glob member; checkpoint keys required: `state, cin=6, nctx=5, arch='gru', layers, norm{mu(4), sd(4)}, ctx_mu(5), ctx_sd(5)` (`scripts/crm_train.py:124-127` writes exactly these; verified on `CRM_N2_s0.pt` and `N2_s0.pt`: nctx 5, ctx_cols [17..21], 256,677 params).
- Forward: `Net.forward(x (B,6,96,32), ctx (B,nctx)) -> hazard (B,96)`; `route_logit = log(sum softplus + 1e-6)`; `P = 1-exp(-exp z)` (`gen_riskmodel.py:10-12, 42-57`).
- Planner path: `f104_n2_iter.member_logits(model, X, ctx5, bs=256)` (`:153-167`) normalises channels 0-3 per member, appends a ones channel, normalises ctx, loops members -> `Z (members, n)`; `Scorer.__call__` returns `(Z, Z.mean(0), Z.max(0))` after float16 rounding of X and `geom_ctx = [goal_dx, goal_dy, |goal-start|, start_yaw, route_len]` per candidate (`f104_n2_iter.py:170-182`, `gen_planner.py:149-151`). Objectives mean/pess/expected_cost (`:185-193`). Batch <= 256, but CEM calls it 5-6 times with <= 64 candidates.
- Context today is geometry only; the plan's statement that the specialists are not history-conditioned is correct. No vehicle state reaches the model even though the dataset ctx is 22-d (17-d anchor state + 5 geometry, `f104_n2_dataset.py:113-115`). `n2_arch_train.py` has `vel`/`chassis` ctx variants (`:19`) but saves `GRUNet` with `model_kind='n2_arch_train'` (`:305`) which `RiskModel` cannot load.
- Latency (RTX 5090, per start-goal pair, incl. numpy sampling/validation): A 0.48 s, B (CEM 4x64) 0.55 s, C (8x64) 1.02 s (`iter_crm/summary.json` `wall_s_per_group`). Gradient arm 22.8 s.
- One code path for a per-decision context z: compute z once in `Scorer.__init__` (history -> encoder), and in `__call__` pass `ctx = concat([geom_ctx(n,5), repeat(z, n)])`; `member_logits` then needs `ck['ctx_mu']/ctx_sd` of matching width and `RiskModel` a branch on `ck.get('model_kind')`. Nothing else in `plan_iter` touches the model.

## 4. Are the two suites paired across domains? No

Different pairs: 0 exact matches, min 4-D distance 2.02 m between `f104_crm_eval_group_*` and `f104_g1_test_group_*` (verified). Different regimes too: CRM suite is speed-free (arms A-F), the rigid f104 suite is fixed-2 m/s (speed-free rigid f104 is at ceiling: gen_v1 model unsafe 0.0 %, g216/g231 goal 98-100 %, `crm_night2_v1/REPORT.md:116-141`). Map sources differ (OptiX depth image vs heightmap; equal to float16 rounding, `crm_f104_v1/LOG.md:12`).

How to build a paired suite: run `planner_arms.py` on the SAME `--cases` dir for both worlds (any case dir with `route_00.json` works; the reference-pick check just reports MISSING). For rigid drives ship that case dir under `GEN_ROOT` and set `--case-prefix`; for CRM set `--task-root` so `case` paths resolve under `CRM_ROOT`. Recommended: `cases_eval/cases` in both worlds (its rigid outcomes do not exist yet; 200 groups x ~5 distinct routes ~ 1,000 rigid drives, 11-25 min per 16-core shard).

## 5. Startup context at the planning decision

Both collectors run a 0.8 s braked settle (`traverse_fdm_rgbd_diverse_chrono.py:29`, `crm_collect.py:168, 204`) and record from frame 0 only; `anchor_state.npz.history` (16 x 24 = 17 state + 3 action + ego xy + sin/cos yaw) is `build_history` padding: the single settled state repeated 16 times with a synthetic brake action (`fdm_data.py:79-93`; verified: all 16 vx rows identical on a rigid run). So at the decision the observable history is one state at rest (vx about -0.03 to -0.15 m/s, roll/pitch, four tire Fz, wheel omegas). The offline harness plans from `layout.start_*` before any drive; the online runners also plan from the layout pose with no state (`gen_mission_runner.py:109-117`). "Startup vs established history" therefore cannot be measured with the current offline-pick harness.

## Gaps / unknowns

- Whether rigid-world drives of the CRM eval routes exist (`crm_f104_v1/PLAN.md:67-78` mentions "rigid-twin outcome rates as context"); not checked.
- Local `eval_iter_crm/runs/*` hold only trajectory/outcome/episode_complete/collection_request; `anchor_state.npz`, `case.json`, `command_reference.npz` were not synced back (present for rigid runs).
- The tasks.json -> tasks_cluster.json route-prefix rewrite for CEM arms is not a saved script.
- Tire Fz at rest differs between soil and rigid ground; whether that counts as an allowed observable for the history branch is a plan decision, not verified here.
- Statistical power: with 200 groups the paired 95 % CI half-width on a near-zero difference was about 2-2.5 pts on CRM (E:B [1.0, 5.5]) and 1.5-2 pts on rigid; a 2-pt non-inferiority margin is at the edge on CRM.

2. Name the baseline arm for "specialist performance": CRM one-shot A 91.0 % vs CEM 4x64 B 98.5 % (`eval_iter_crm/analysis.txt`); rigid fixed-2 A 99.0 % / B 100 %.
3. Add an explicit id blacklist (`f104_crm_eval_group_*`, `f104_g1_test_group_*`, any new paired set) to the new dataset builder, and override `split` for held-out pools; the hash split alone does not protect them.
4. Extend `RiskModel`/`member_logits` with a `model_kind` branch and a wider ctx so a `[geom(5) | z]` context is one code path; keep `Scorer` computing z once per decision.
5. Evaluating "startup vs established history" needs either an in-process planner call after the settle (nav_runner/gen_mission_runner style, `GEN_SRC/GEN_MODELS` env, `gen_planner.py:20-22`) or a moving-anchor replan protocol with full CRM soil restore (plan step 4); the offline-pick harness cannot do it.
6. Either raise the group count (~600-1,000 pairs) or widen the predeclared gap; report the feature-clustered CI (`n2_cluster_ci.py`) as the honest interval.
